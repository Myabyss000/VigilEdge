VigilEdge-ThreatLoom: A Local Hybrid WAF-SOC Architecture for Real-Time Web Threat Detection and Automated Response

IEEE Author Block

Author details are intentionally omitted for double-blind review.

Abstract

This paper presents a hybrid WAF-SOC architecture, VigilEdge-ThreatLoom, for local web defense where cloud-managed security may be impractical because of cost, policy, or connectivity constraints. The implemented system links inline Web Application Firewall (WAF) enforcement with downstream Security Operations Center (SOC) analytics and playbook-driven response. We evaluate three profiles: signature-only WAF (A), WAF plus SOC rule analytics (B), and full hybrid WAF-SOC architecture with response orchestration (C). Measured metrics include precision, recall, F1-score, false positive rate (FPR), p50/p95 latency, and throughput; mitigation delay was not measured in this run because end-to-end response timing instrumentation is incomplete for profiles B and C. Results show identical recall across profiles (1.0000), while profile B exhibits severe false positives (FPR = 1.0000), demonstrating calibration risk. Profiles A and C provide the best quality balance in this workload, with C adding stronger operational visibility and response capability. The contribution is an evidence-bounded, reproducible local security design and evaluation workflow.

Index Terms

Web application firewall, SOC automation, hybrid detection, incident response, local cybersecurity.

I. INTRODUCTION

Web applications continue to represent a dominant external attack surface. Common adversarial traffic includes SQL injection, cross-site scripting, path traversal, command injection, and request-flood abuse. While cloud edge platforms provide robust protective controls, many organizations still require local deployment due to data governance boundaries, air-gapped operation, budget constraints, or educational-lab conditions.

In local deployments, rule-based WAF filtering is widely used but frequently isolated from downstream operational context. As a result, campaign-level behavior and cross-event progression may remain underdetected, and mitigation decisions may remain manual or delayed. This paper evaluates whether a hybrid WAF-SOC architecture can improve practical local defense outcomes while maintaining acceptable runtime overhead.

A. Problem Statement

Signature-only local WAF deployments exhibit three practical limitations: 1. Per-request analysis with limited temporal context. 2. Weak visibility of distributed and low-and-slow attack behavior. 3. Fragmented detection-to-response execution paths.

B. Research Question

Can a local hybrid WAF-SOC architecture improve detection and response effectiveness compared to signature-only local filtering, while preserving acceptable latency and throughput under local test conditions?

C. Contributions

This paper makes four contributions: 1. A local, modular architecture coupling inline WAF enforcement with SOC analytics and automated response. 2. A staged hybrid detection model integrating signature, threshold, behavioral, and time-window correlation logic. 3. A reproducible experimental protocol for quality and performance benchmarking. 4. A deployment-focused analysis of limitations, validity risks, and safe operational boundaries.

D. Innovation Statement

The core innovation is not a new single detector, but an accessibility-first and deployment-first security architecture that unifies prevention and operations in a local environment. Specifically, the system combines low-cost deployment, offline-capable execution, reproducible evaluation artifacts, and analyst-governed automation in one integrated stack. This positions the work as a practical bridge between basic local firewalls and high-cost cloud-managed security ecosystems.

Example use case: a small business owner running one public-facing web service on a low-cost VPS can deploy this architecture locally to gain both request-time filtering and SOC-style incident visibility without subscribing to enterprise cloud-edge tooling.

II. RELATED WORK

Conventional local WAF systems prioritize deterministic pattern matching and low request-path latency. SOC and SIEM systems emphasize event aggregation, correlation, and analyst workflow support. Cloud edge providers combine these capabilities with internet-scale telemetry and challenge ecosystems. However, local implementations that integrate all layers in one coherent, reproducible pipeline remain less common. Threat taxonomies and vulnerability prioritization are well documented by OWASP and MITRE, but those references do not provide a low-cost integrated local operations blueprint [@owasp_top10_2021; @mitre_attack].

VigilEdge-ThreatLoom is positioned as a hybrid WAF-SOC architecture rather than a cloud-equivalent edge system. The novelty is not a standalone pattern set, but a coupled detection and response pipeline in which inline decisions, contextual analytics, and bounded automation are operationally linked.

III. ARCHITECTURE OVERVIEW

The system is organized into four layers.

A. Inline Enforcement Layer (VigilEdge)

The WAF inspects HTTP traffic and applies attack-class checks including SQLi, XSS, traversal, and command-injection style payloads. It enforces allow, block, or rate-limit actions and emits structured event records.

B. Ingestion and Normalization Layer (ThreatLoom)

ThreatLoom ingests event streams through API endpoints and normalizes key fields, including source IP, path, action, attack type, severity, and timestamps.

C. Detection and Correlation Layer

The SOC engine executes signature and threshold rules, runs behavioral analyzers, and performs IP/session/time-window correlation to identify repeated and escalating activity.

D. Response Orchestration Layer

Playbook triggers map alert conditions to actions such as block, temporary ban, and adaptive rate limit. Action state is tracked, auditable, and revocable.

E. Accessibility and Deployment-by-Design

The architecture is intentionally designed for environments where cloud-edge security is unavailable or operationally unsuitable. This includes academic labs, resource-constrained teams, private intranet services, and policy-restricted deployments. The system is designed to run on commodity hardware, expose transparent controls, and preserve reproducibility with script-driven experiments and local artifacts.

IV. DETECTION AND RESPONSE PIPELINE

The pipeline proceeds in stages: 1. Inline signature and policy enforcement. 2. Event enrichment and normalized persistence. 3. Rule and threshold analytics in SOC processing cycles. 4. Behavioral and temporal correlation. 5. Playbook-based mitigation with override support.

This staged strategy aims to preserve low-latency inline filtering while increasing post-ingestion context depth for higher-confidence operations decisions.

A. Detailed System Flow (Request to Mitigation)

  1. A request enters the WAF and is normalized (path, query, headers, payload fingerprints).
  2. Signature and policy checks produce an immediate decision: allow, block, or rate-limit.
  3. A structured event is emitted with source, action, severity, threat class, and timestamp.
  4. ThreatLoom ingests and normalizes the event into SOC-ready fields.
  5. Rule engines evaluate threshold conditions across time windows.
  6. Behavioral correlators evaluate repeated probing, burst anomalies, and escalation patterns.
  7. If trigger conditions are met, a playbook action is selected and executed.
  8. Response outcomes are recorded with audit metadata and optional revocation support.

B. Module Data Flow and Event Structure

Events are transferred from WAF to SOC as JSON records over REST endpoints. A minimal event schema includes: event_id, timestamp, source_ip, request_path, http_method, action (allow/block/rate_limit), threat_type, severity, rule_id, and context_tags.

This explicit event contract enables downstream correlation and response without re-parsing raw HTTP traffic in the SOC layer.

C. Internal Working Logic

The internal operation uses two linked decision loops:

  1. Inline decision loop (fast path):
  • Input: request features and signature matches.
  • Output: immediate enforcement action with minimal latency impact.
  1. SOC decision loop (context path):
  • Input: event stream over temporal windows.
  • Output: contextual alerting and bounded response actions.

A simplified scoring view is: Riskt = wsSt + wtTt + wbBt + wcCt where: - St: signature confidence score at time window t. - Tt: threshold/rate pressure score at time window t. - Bt: behavioral anomaly score at time window t. - Ct: correlation consistency score at time window t. - ws, wt, wb, wc: weighting coefficients. - τ: trigger threshold for playbook execution.

In simplified operation, the four components are normalized into comparable ranges and combined by weighted summation. If Riskt ≥ τ, the system evaluates response policy constraints and executes the selected action.

This two-loop design is the practical mechanism by which the system avoids relying only on per-request signatures while still preserving fast inline protection.

V. IMPLEMENTATION DETAILS

The implementation is Python-based and service-oriented. The WAF and SOC services expose HTTP/REST interfaces and exchange structured JSON events. In this implementation, the web and API stack is built around FastAPI/Uvicorn style services, with rule/playbook configuration files and relational persistence for SOC entities.

A. Execution Model

The implementation follows a split execution model: 1. Synchronous path for inline request mediation (WAF). 2. Asynchronous path for SOC analytics and response orchestration.

This split limits user-visible latency while enabling richer post-ingestion reasoning. It is also a key engineering tradeoff in local deployments where compute resources are finite.

B. Operational Safety Controls

  • Role-based access for sensitive APIs.
  • Response cooldown and revocation pathways.
  • Alert deduplication windows to reduce analyst fatigue.
  • Structured logs and event metadata for traceability.

C. Enforcement Logic (Rate Limiting and Blocking)

Rate limiting and blocking are driven by per-source counters and threshold windows. At a simplified level, repeated suspicious requests within a configured window increment risk and can escalate actions from allow to rate-limit to block.

Blocking state is maintained with timestamped entries so temporary actions can expire or be revoked. This avoids permanent lockout by default and supports analyst override.

D. Behavioral Analysis Example

Example: if a source submits benign-seeming requests at low volume and then rapidly shifts to repeated traversal patterns within a short interval, the behavioral module raises anomaly pressure even when each individual request alone appears borderline. This enables earlier detection of campaign-style progression.

E. Logging and Storage

The architecture uses structured security events (JSON payloads) for inter-module communication and persists SOC-side entities (alerts, incidents, response actions) in backend storage. Logs include at least timestamp, source, action, and threat metadata to support audit and replay.

F. Deployment Scope and Actual Setup Process

Current scope supports single-application deployment on a single node.

Practical setup steps used in this project are: 1. Clone the repository. 2. Create and activate Python virtual environments for the WAF and SOC services. 3. Install dependencies from requirements.txt in each service directory. 4. Configure service environment variables and local target URLs. 5. Start the protected demo application. 6. Start the WAF service. 7. Start the SOC service. 8. Run benchmark scripts and review generated artifacts.

One-command deployment is not currently implemented; it is future work.

D. Discussion of Measured Outcomes

Three observations are most relevant for publication claims. First, recall was 1.0000 for all three profiles in this workload, indicating that attack-like requests were consistently intercepted. Second, Profile C matched Profile A on detection quality metrics while preserving similar end-to-end performance, which supports the feasibility of local hybrid defense without obvious catastrophic overhead under the tested conditions. Third, Profile B produced a pathological false positive profile (FPR = 1.0000), indicating a policy calibration problem rather than an architectural ceiling.

The runtime data should be interpreted with the same caution. Although Profile B reported higher throughput and lower p95 latency, those gains are coupled to indiscriminate blocking and therefore are not operationally acceptable. Consequently, the primary contribution is not that every layered configuration improves outcomes, but that measurable cross-layer observability exposes when policy settings become unsafe and enables systematic correction.

Profile B failure is attributable to over-aggressive thresholds, insufficient calibration against benign traffic, and absence of stronger scoring moderation in this run configuration. This is a system-tuning lesson rather than evidence against the hybrid WAF-SOC architecture.

Profile C is preferable to Profile A despite similar aggregate metrics because C provides richer operational visibility (correlated alerts/incidents), explicit response lifecycle records, and governed automation pathways that A does not provide.

There is an explicit trade-off between latency and detection depth: adding SOC-side context analysis can increase processing complexity, but it can also improve operational decision quality and reduce hidden campaign progression risk when calibrated properly.

False positives directly affect usability by interrupting legitimate user traffic and increasing analyst burden. Therefore, controlling FPR is critical for real-world deployment viability, not merely a reporting metric.

In the camera-ready version, this section should include repeated-run confidence intervals and a tuned rerun of Profile B to distinguish architecture effects from configuration artifacts.

F. Strong Analysis of Utility and Differentiation

Practical utility is established along three axes. First, security utility: the system sustains perfect recall in this workload while exposing false-positive behavior explicitly. Second, operational utility: the architecture links detection to auditable and revocable response actions, reducing manual SOC burden. Third, deployment utility: the stack can be executed locally with transparent controls, which is critical for institutions that cannot depend on managed cloud-edge services.

Differentiation is also explicit. Compared to a signature-only local WAF, this design adds temporal and behavioral reasoning plus response orchestration. Compared to cloud-edge platforms, this design prioritizes accessibility, local control, and reproducibility over global telemetry scale. The contribution is therefore best understood as a deployable, evidence-backed middle layer between basic local filtering and enterprise cloud-edge ecosystems.

The benchmark outcomes establish a clear comparative narrative under local test conditions: Profile A and Profile C maintain the strongest quality balance in this run, while Profile B reveals a calibration failure mode (overblocking) that is explicitly documented as an operational risk rather than hidden in aggregate metrics.

VIII. THREATS TO VALIDITY

  1. Internal validity: residual configuration drift between runs.
  2. External validity: synthetic workload bias versus production traffic.
  3. Construct validity: label quality for borderline payloads.
  4. Systems validity: machine-level performance variation.

IX. LIMITATIONS

  • Rule quality and maintenance cadence remain critical.
  • Local threat intelligence breadth is inherently limited versus global edge systems.
  • Aggressive automation can increase false-positive impact.
  • Single-node deployments may constrain high-load behavior.
  • Current implementation supports single-application deployment in one-node mode.
  • Distributed scaling and multi-node coordination are not yet implemented.
  • Machine-learning-based adaptive detection is not included in the current version.

X. ETHICAL AND RESPONSIBLE USE CONSIDERATIONS

All testing and evaluation must be executed on authorized assets and controlled targets. The system and methodology are intended for defensive cybersecurity research and operations only.

XI. CONCLUSION

This study demonstrates that a hybrid WAF-SOC architecture can be implemented and evaluated in a local deployment with reproducible artifacts. In the measured workload, all profiles reached recall of 1.0000, while calibration quality determined usability: profile B overblocked benign traffic, whereas profiles A and C retained stronger quality balance. The work therefore proves not that every layered configuration is better, but that integrated architecture plus calibration-aware evaluation provides actionable security and operations insight. Future improvements should focus on mitigation-delay instrumentation, repeated-trial statistics, and tuned policy thresholds.

XIV. PROFESSOR QUESTION ALIGNMENT

A. What Problem Was Solved

This work addresses a common gap in local cybersecurity deployments: request-level signature filtering is often disconnected from SOC context and automated response lifecycle control. The paper solves this by integrating WAF prevention and SOC operations into one local pipeline.

B. How the System Works

The system operates through a staged dual-loop process: fast inline WAF enforcement for immediate protection, followed by SOC-side temporal/correlation analysis and policy-bounded playbook response. Section IV provides the detailed request-to-mitigation flow and internal risk decision logic.

C. Why It Is Useful

The system is useful because it provides actionable defense-in-depth in local environments: measurable threat detection, operationally visible alerts/incidents, and bounded automation with auditability and revocation. It also supports reproducibility through scripts and benchmark artifacts.

D. What Makes It Different

The key differentiator is accessibility plus deployment-by-design. Unlike cloud-edge systems, this architecture is intended for low-cost local execution with transparent controls. Unlike standalone local WAFs, it provides SOC-level context reasoning and response orchestration. This combined property is the main innovation claim of the paper.
